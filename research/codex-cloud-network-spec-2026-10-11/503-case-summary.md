# 503が出た場合と正常な場合の違い

2026年10月11日の保存済み記録を比較した。時刻はJST。最新の60分比較窓は18:40:02.220146終了。以前の固定集計は17:46:09終了として区別する。20:45:24の初429は別の追加観測として記録する。

**アクセス負荷と休止時間に違いがあり、レート制限や中継資源の回復という仮説は観測と整合する。ただし原因・制限の単位・時間窓・閾値は確定していない。**

その後、休止と減速を伴う完了25区間では、10月12日13:09:32までの16,072実GETで共通503と429が各0件だった。これは前半との大きな差だが、TLS・接続終了を示す503は43件、通常HTTP 503は24件あり、取得全体の成功を意味しない。また、0.25 RPSで429が出た実例もあるため、0.25や0.35 RPSを公式の安全閾値とは扱わない。[固定25区間の原ログと集計](post-429-twenty-five-complete-batches.json)、[初429の応答](first-429-observation.md)を参照。

証明書検証失敗を示す503には、休止・時間経過で戻った共通503とは異なる例がある。マミヤ・オーピーの同じrobots URLは、10月12日08:10:40と08:55:26の実dispatch（間隔2,685.834698秒、どちらも0.25 RPS）でともに `CERTIFICATE_VERIFY_FAILED` を返した。企業本文は両方とも未GETであり、受付拒否の根拠にはならない。この応答だけで失敗したTLS区間や、同時にレート制限がなかったことまでは確定できない。[同一URLの2応答と原資料SHA](repeated-certificate-503-7991.json)を参照。

上限0.35 RPSの60社は372実GETで完了した。次の区間も26/60社・191実GET時点で共通503と429が0件だったが、通常503を受け0.28、0.25へ減速している。0.35は調査側の試行値で、公式の安全閾値ではない。

最新の完全60分窓は上限変更後だけを含む。保存893 GETの取得時設定は0.25 RPSが799件、0.28が92件、0.35が2件で、collectorは4 workersだった。同じ窓には通常503が4件、TLS 503が4件、connection termination 503が1件ある。共通503が0件でも各サイトの取得がすべて正常とは扱わない。時刻付き保存ログに対応しないGETもあり、今回の窓に重なる2 runのcollector計数からは窓内900〜913件の範囲となる。接続先の構成、休止と時間経過も変わっているため、負荷だけの因果を確定しない。

直近の固定60分窓ではcollector報告1,226 GET、時刻付き保存1,181件、差45件、観測263 originsだった。この窓には上限変更前の取得も含み、0.35 RPSで1時間一定に取得した実験ではない。過去の1,597件とは計数方法の差にも注意する。

共通503は `Invalid argument|remote address:envoy://cloudflare_https_tunnel/` を含む。TLS証明書関連や通常の503を別に集計し、すべての503をレート制限とは解釈しない。18:40:02までの固定比較範囲に429はなく、共通503に待機時間の指定もない。301の `Retry-After: 0` が1件あるが、待機を要求した制限応答ではない。

成功・失敗の両方でruntimeは `unrestricted / unknown`、設定revision・観測revisionは6だった。`unknown` だけでは成否を説明できず、これを設定未適用や障害原因と断定しない。取得できた公式資料には数値quotaとこのエラーの対応が記載されていない。

調査は単一collectorでrobots・redirect・preflightを含めて合算し、上限0.35 RPSとサイト別の間隔を維持する。共通障害や429には減速・休止を行う。企業の受付拒否や窓口不存在とは分類しない。
