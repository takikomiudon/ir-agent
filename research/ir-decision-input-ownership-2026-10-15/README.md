# 数値判断入力の供給主体と、待つ根拠の境界

2026-10-15。現行契約のローカル読取整理。新しい金融方針・値・採用記録・利用者承認を作らない。実DB照会、GET、コード・元資料の変更は0。過去の著者3者の表現可能性判定を再実施していない。

現行APIは、6必須パラメーターの明示値について `user` と `external_policy` のどちらも受け付ける。`synthetic_example` は実判断へ転用できない。[C:22–54,151–157] 費用や価格鮮度を投資著者だけから得る契約ではなく、**費用・鮮度を含むすべての不足を「著者の追加説明待ち」へまとめる必要はない**。ただし、供給主体を分けることは値の採用や必須条件の削除ではない。利用者の「既存の方針を第一に」という指示を、エージェントの値決定へ読み替えない。[P:61–69]

「著者本人が明示的に不要と言うまで必須」は、現行コードにない追加解釈である。現行の6必須は本プロジェクトの数値判断APIの共通条件であり、著者が不要と述べても自動で外れない。一方、著者に記載がない項目を利用者・執行条件の採用記録から供給する経路は、既に許されている。[C:15–54,154–160; P:49–51,63–65] 原文の存在、採用者による適用、会社別入力の充足を区別する。

## 適用限界と、待ち状態の分け方

次の作業は、既存の不足を上表の所有者へ割り当て直すこと。投資規則の意味・対象期・適用範囲が足りないなら著者根拠、会社の実績や指標定義が足りないなら会社公表事実、費用・保有・精度受容なら利用者／執行条件、価格fieldや観測精度ならデータ契約の確認として記録する。混合項目は両方の根拠を分け、片方の確認で全体を充足済みにしない。会社IRに投資家のリスク許容率・個人保有・著者の意図を質問して埋めない。[P:59; M:13,42]

構造検証はnullを許すが、数値判断は6値の不足を `policy_not_configured` としてposition確認等より先に返す。[C:34–35,154–160] この順序のため費用不要に見える枝でも、現APIでその設定を省略できるとは解釈しない。設定・出典ラベルの形式が通っても経済的妥当性・正しい採用は証明されない。[W:189,193]

数値判断の未完と、会社事実・反証・研究上のモデル適合の点検待ちも分ける。部分研究は関係ない入力を一律要求せず、未確認はfalseや数値0へ変えない。[P:49–51; M:29,84–88] 本整理は既存gateを緩める提案でも、新しいpolicyへの承認依頼でもない。
