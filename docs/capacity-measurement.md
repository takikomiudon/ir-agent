# IR調査の作業量と滞留を記録する

[運用設計13節](ir-operation-design.md#13-実測から日次能力と優先順位を更新する)を、読取り専用の計測レポートへ実装した。入力された試行・利用量・評価窓・明示した運用者の予算を集計する。金融著者による運用算式ではなく、**本プロジェクトの計測への適応**である。

```bash
.venv/bin/python scripts/report_research_capacity.py examples/work-measurements.json
```

`--output FILE` でJSONを保存できる。Python APIは `report_research_capacity(request)`。DB更新、スケジューラ起動、モデル実行、企業への通信を行わない。[入力例](../examples/work-measurements.json)の作業・予算は全て `synthetic: true` の架空値で、推奨予算や実測した投資分析の所要時間ではない。

## 入力

最上位は `schema_version: 1`、`window`、`measurements`、任意の `operator_capacity`。時刻は全てオフセット付きISO日時。`window.started_at < window.ended_at` が必要。日付だけから営業時間や締め時刻を補わない。

| フィールド | 定義 |
|---|---|
| `id` | 不変の計測レコードID。同じ入力内の同ID・同内容の再送は1件にまとめ、変更はエラー。別ファイルとの履歴照合を永続的に行う台帳機能はない。 |
| `company_id` | 対象会社の識別子。1社の1段階完了を、その会社の全投資分析完了にしない。 |
| `stage` | 開示点検・深掘り・反証・質問作成・返信評価・価格再点検等。空でない名称を明示する。異なる段階を同コストと仮定しない。 |
| `worker_id` | 作業担当の識別子。同じ担当を複数IDで記録して並列数を水増ししない。 |
| `attempt_id` | 物理的な1試行の安定した識別子。再試行は新しい識別子にする。同じ会社・段階・担当・試行を別の `id` で重複計上するとエラー。 |
| `started_at`, `ended_at` | 試行の開始・終了の壁時計時刻。未完は `ended_at: null`。経過時間であり実作業時間とは異なる。 |
| `status` | `completed`、`failed`、`retry`、`in_progress`、`cancelled`。`retry` は「終了した試行が再試行を要した」記録。未完だけが終了時刻null。 |
| `active_seconds` | 任意。実際に計測したworker実作業時間の秒数。待ち・中断を分離できなければnull。終了試行では経過時間を超えられない。 |
| `tokens` | 任意。明示した試行の総トークン整数。得られなければnull。入力/出力内訳を推測せず、API側の利用量が分かる場合に集計して記録する。 |
| `cost` | 任意。`{"amount":"…","currency":"JPY"}` 等。実際に記録した試行費用。同じ通貨でのみ加算する。 |
| `synthetic` | 任意の真偽値。trueの架空記録は観測記録と別コホートで集計。省略は呼出側が観測記録として渡した扱いであり、実行の真正性をソフトウェアが証明するものではない。 |

`active_seconds` と費用は非負の数値又は数値文字列。0は「計測した0」、nullは「不明」。秒数・金額の出力はDecimalの文字列、トークンと件数は整数で返す。分布の `p50` / `p90` はソートしたサンプルのnearest-rankで、予測値や信頼区間ではない。

1レポート内には各物理試行の状態を1つだけ渡す。未完から完了への状態変化を、同じバッチ内に「別の物理試行」として追加しない。終了記録の収集や状態履歴の保存は呼出側で整える。

`operator_capacity` は評価窓について運用者が明示する合計worker秒数、費用予算である。

```json
{
  "worker_seconds": null,
  "cost_budget": null,
  "synthetic": false
}
```

値がなければnull。worker人数×営業時間を勝手に補わない。架空予算を使う例では `synthetic: true` を付ける。実予算と架空試行、架空予算と観測試行を比較しない。通貨変換は行わない。

## 何を集計するか

- 終了イベントの窓は `[開始, 終了)`。窓の終端ちょうどの終了は別件数にする。区間の経過時間は窓と重なる部分だけを測る。
- 期間外、失敗、再試行、取消、窓末の未完を区別する。失敗・再試行に使った時間・トークン・費用も除かない。
- 窓内で開始・終了した試行について、実作業時間と経過時間を別々に段階別分布へ入れる。窓をまたぐ試行や未完の試行について、総active・トークン・費用を窓内へ比例配賦しない。欠損を含む窓全体の利用量はnullとし、既知の試行の合計と不足件数を併記する。
- 同じworkerの時間区間をunionして、占有経過時間と重複を返す。異なるworkerが同時に占有された数も、このunion後の区間から数える。占有経過時間を実作業時間や利用可能な能力として扱わない。
- 同じworkerに時間の重複があれば、実作業区間の内訳がないのでworker実作業合計はnullにする。記録された試行別activeの合計は監査用に残し、予算との比較には使わない。段階別分布・段階別usageは試行観測の合計で、並列workerの能力ではない。
- 未完として観測した試行の件数と開始以来の長さを返す。受付前・未開始の需要、待ち行列への到着時刻、期限を入力していないため、待ち時間・期限超過はnull。開始以来の経過を「待ち」と呼ばない。

`completed_attempts` と `completed_company_coverage` は、指定窓で完了イベントを観測した試行数と会社数である。例えば同じ会社の資料点検と価格再点検が完了すれば2試行・1社。仮説・反証・価格条件まで全て検証した1社、毎日監視可能な1社、問い合わせ可能な1社が完成したという意味ではない。

予算比較は、対象コホートと予算の架空/観測区分が一致し、実作業の欠損・窓跨ぎ・同worker重複がない場合のworker時間と、費用が揃い通貨が一致する場合に限る。予算超過なら差は負になる。比較できない項目はnullを返す。

## 会社数の上限へ飛躍しない

`company_upper_bound` はnull、`capacity_status` は `not_estimated`。予算が明示されても、限られた段階・試行だけから全運用の上限を出さない。「各社を毎日同じ時間調べる」「workerを倍にすれば会社数が倍になる」は採用していない。

次の測定は、実際の到来/未開始需要・期限、通常日と決算集中日、再作業を含む段階構成、共有API・DB制約、同一会社の排他、反証担当の時間、全工程の完了件数である。公開開示だけの監視、深掘り、問い合わせ中、保有の各対象を分ける。架空デモや資料取得だけの速度を、実際の金融分析能力へ転用しない。

## 計測時の時計

開始・終了の壁時計と、実作業区間の長さを区別する。Pythonの [`time.perf_counter_ns`](https://docs.python.org/3/library/time.html#time.perf_counter_ns) は短い区間の経過計測に使えるが、待ちやsleepも含むため、それだけではactiveの根拠にならない。[`time.monotonic`](https://docs.python.org/3/library/time.html#time.monotonic) のような単調時計の値自体を、公表日時や別マシンの時刻に使わない。各担当で区間差を測り、明示した実作業区間だけを累計する。実作業とAPI待機等を分けられない既存ログは、無理にactiveへ変換せず欠損として扱う。

上の時計の公式参照は計測上の説明であり、本レポートの算式を金融著者に帰属させるものではない。数値処理の一次仕様は [capacity.py](../src/ir_agent/capacity.py) と [回帰テスト](../tests/test_capacity.py) にある。
