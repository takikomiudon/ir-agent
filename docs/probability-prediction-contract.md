# 条件付き信号予測を事前保存し、実観測へ接続する契約

**全体の接続は設計案。予測の不変保存・readiness監査は実装済み、採点接続は未実装。** IR信号の確率予測を回答前にDBへ固定し、後で独立に確認した状態に対応する一行だけを採点するための契約。現行の観測台帳・訂正履歴・純粋な採点関数を再利用する。実際の確率、尤度推定法、標本数、採用点、投資条件、重みは追加しない。

[保存API](probability-prediction-storage.md)と[readiness監査](prediction-readiness.md)の実装範囲は各文書で区別する。実台帳の予測は0件であり、この接続案を実観測の採点、IRの正確性・収益性の確認と解釈しない。以下の将来の包括評価保存APIは未実装。

## 原典が支持するものと、この設計で決めるもの

[保存済み文献調査](../research/probabilistic-evaluation-2026-10-15/README.md)の原文・引用・式の確認を根拠とする。追加取得は行わない。

| 根拠 | 採用する原則 | この設計への適応と限界 |
|---|---|---|
| Gneiting–Raftery (2007)、PDF1・5・14ページ | 実現事象に対し事前の確率予測を採点する。Brierとlogのpropernessは期待スコアの性質であり、一件の好成績が真の分布を証明しない。 | 送信前のDB固定、観測とのID・版・SHA結合、状態別行の選択は本プロジェクトのAPI設計である。原典が日本株IRの尤度や必要件数を与えるわけではない。 |
| 同論文、PDF5ページ | 全カテゴリのBrier式とlog式、観測カテゴリの予測確率0でlog rewardが負の無限大となる境界。 | 現行計算器は小さい方がよいlossへ符号を反転する。全カテゴリ和、自然対数、無限大のJSON表現を固定する。独自の平滑化やepsilonを加えない。 |
| scikit-learn公式のgroup/time分割の説明 | 同一groupの混入と、時間依存を無視した学習・評価の混合に注意する。 | IRでの企業・決算期・質問群と、実際の情報利用可能時刻を明示する。既定の分割器、fold数、均等な観測間隔をそのまま採用しない。金融戦略の原論文としては扱わない。 |

式と現在の関数仕様は [probability-scoring.md](probability-scoring.md) にある。OTextsの章は原文欠損のため採用根拠に含めない。EVSIとの関係は [観測設計](ir-outcome-observation.md) に従い、採点結果だけで尤度の校正やEVSIの妥当性が確認されたことにしない。

## 1. 既存の観測を母集団として維持する

分析単位は既存の `observation_id`、すなわち会社×質問の一観測を再利用する。既存の `company_id`、`question_id`、`cohort_id`、`design_version`、状態定義、`state_timing`、対象期間、signals、返信待ち期限、状態判定期限を予測台帳側で再定義しない。

予測のない観測、未送信、到達失敗・不明、期限前、無回答の受信確認不足、状態未判定、公開性保留、外部変化による状態推定不能も、元の観測IDのまま残す。予測と観測を内部結合して、対応しなかった案件を報告から消さない。観測台帳を母集団とする左結合を使い、予測登録側にだけ存在する不正参照も別途エラーとして数える。

既存cohortの定義ハッシュには `state_timing`、states、target_period、signals、synthetic区分が含まれる。予測はその定義を同じ方法で照合する。異なる期間・状態定義・質問型を混ぜるには別の評価設計が必要であり、同じ文字列のsignal名だけを理由に同じ母集団へ束ねない。

## 2. 最小の予測登録レコード

次は**未実装の保存契約案**であり、そのまま現行CLIに投入できるJSONではない。予測値を含む本体は一度保存したら変更しない。行列の方向は既存EVSI入力と合わせ、`likelihoods[signal][state] = P(signal | state)` とする。

| 欄 | 必要な内容・検証 |
|---|---|
| `id` | 一意の予測ID。同ID・同内容の再送は冪等とし、別内容の再利用を拒否する。 |
| `observation_ref` | 既存観測のID、登録時の版、snapshot SHA、`design_sha256`。参照先は実際の同じDBで解決する。会社・質問・cohort・定義は参照snapshotから導出する。 |
| `model_ref` | モデルID・版、設定・コードまたは保存モデルの不変manifest参照とSHA、学習完了時刻。単なる名前の申告だけで同じモデルと認定しない。 |
| `training_ref` | 学習に使用した観測ID・版・分類訂正版・根拠snapshotを特定するmanifest参照とSHA、学習情報の利用可能締切。外部モデルならその根拠と確認できる範囲を記録する。 |
| `created_at` | 予測を生成・確定したオフセット付き日時。自己申告の生成時刻と、DBへの実保存時刻を区別する。 |
| `likelihoods` | 既存設計の全signalをキーとし、各signalが全stateを持つ行列。各stateについて全signalの確率が有限の0〜1、十進値の合計が厳密に1。欠損・自動正規化・事前確率からの補完を行わない。 |
| `provenance` | 実証根拠、利用者の仮定、明示的な架空例を区別する。モデルが出した数値であることと、校正済みであることを区別する。 |
| `first_saved_at` | 保存入口が信頼できる実行時計から付けるDB実保存時刻。callerのJSONから受け取って遡及設定しない。 |
| 保存側の照合結果 | 解決した観測・モデル・学習manifestのSHA、定義ハッシュ、入力本体のSHA、登録条件の点検結果。callerが `verified:true` を指定して代用できない。 |

状態の事前確率はこの採点契約の必須項目ではない。後で観測したstateの条件付きsignal分布を採点するため、状態不明を任意のpriorで埋める必要はない。実際の行列値や学習manifestがない場合は、登録可能な実予測は存在しないと記録し、数値を作って契約を完成させない。

最小の保存拡張として、既存観測へ外部キーを持つ不変の予測テーブルと、不変の評価履歴テーブルを提案する。新しい母集団台帳を作らず、予測を既存観測の `replies` や設計欄へ後付けしてdesign hashを変えない。予測テーブルを参照するためだけに同じ会社・質問へ新しい観測IDを発行しない。

## 3. 実保存を含む時間順序

実案件では、観測設計を先にDBへ登録し、その設計を参照して予測を登録する。保存入口は、参照した版が存在することと、登録時点の履歴に送信・受信・判定が既に記録されていないことを確認する。採点時には後から追記された実際の発生時刻も再確認する。

```text
学習入力が実際に利用可能となった締切
  ≤ 学習完了 ≤ 予測生成 ≤ 予測DB実保存
  ≤ 実際の送信試行 ≤ 返信受信または返信待ち期限の確定信号
```

さらに、観測設計のDB実保存は予測DB実保存以前でなければならない。生成時刻を過去に書いただけの予測、送信後に登録した予測を事前予測として採点しない。時刻が同一でも実行順が重要になる境界は、DB保存順とトランザクションによる参照可能性を使い、表示精度の時刻だけで事前性を認定しない。

予測対象となった回答や状態判定が予測前から入力へ混入していないかを確認する。後続の公開資料、取得時刻、状態判定の記録時刻・DB実保存時刻は別に保存し、資料の対象期が過去であることを理由に学習締切へ戻さない。公表時刻不明の資料は都合のよい公表時刻を作らず、確認できる利用可能性の制限を維持する。

`recorded_at` と `first_saved_at` の両方でas-of可視性を点検する。参照される学習データや訂正が、予測時点のDBに存在したかをmanifestから再現できなければ、時間漏洩を検証済みとしない。外部モデルの履歴が確認できない場合も、自己申告の締切から検証完了へ進めない。

## 4. 実際に観測した条件付き行だけを選ぶ

将来の接続処理は次の順序に限定する。

1. 評価の `as_of` を固定し、`ObservationStore.records_as_of` と同じ実保存時刻の制約で最新の可視snapshotを選ぶ。そのID・版・SHAを評価へ保存する。
2. 観測viewで送信、信号、独立した状態ラベル、公開性、期限、外部変化、可視訂正を点検する。既存の `eligible_for_descriptive_table` は入口の条件であり、DB原文・公開根拠の結合や予測の事前性は別に確認する。可視訂正を理由に採点signalも自動更新せず、第6節の漏洩点検と事前の評価規約に従って採用分類を固定する。
3. 元返信・受信時刻と信号分類の根拠、後続公開資料と状態判定の根拠を保存済み原文へ結び付ける。自己申告のID・引用だけでは独立照合済みとしない。必要な原文・版が不足したら保留する。
4. 実際に確認したstateを `s_observed`、観測signalを `y_observed` とする。全stateについて予測を固定してあっても、採点対象は `probabilities[signal] = likelihoods[signal][s_observed]` の一行だけとする。
5. 既存の純粋関数 `score_categorical_forecast` へ、固定signals、上記確率ベクトル、`observed_category: y_observed`、予測・観測・定義の版付き参照を渡す。
6. 呼出元が行った結合・時点・適格性点検と、純粋関数の出力を分けて保存する。関数が返す未検証フラグを、呼出元が検証したふりをして上書きしない。

実現しなかったstateの行には、この質問について実観測がない。全行を同じsignalで採点したり、条件付き行をpriorで重み付けして観測を増やしたりしない。stateが不明なら採点不可であり、周辺分布や返信から推定したstateで代用しない。`P(signal | state)` と `P(state | signal)` は別の予測課題である。

期限内の最初の返信、同時刻の衝突、期限後返信、期限まで受信確認した無回答の扱いは、既存の観測viewを再利用する。新しい採点処理が、点数のよい返信や後の返信へ選び直す規則を加えない。

## 5. 未観測・保留を欠損のまま保持する

評価要求ごとに全対象を列挙し、少なくとも次の違いを理由付きで返す。これらは新設計の分類であり、現行APIの列挙値を追加するものではない。

| 状況 | 扱い |
|---|---|
| 予測未登録、参照不一致、送信後の予測保存 | 事前予測として採点しない。元観測を母集団から消さない。 |
| 未送信、到達失敗・不明 | 企業の無回答signalへ変換しない。 |
| 返信期限前、期限までの受信確認不足 | 信号未確定。将来の無回答を先取りしない。 |
| state未判定、識別不能、定義不一致、状態変化 | 条件付き行を選べない。欠損を0点や不正解にしない。 |
| 公開性保留、分類衝突、未解決の外部変化、根拠未結合 | 適格性が不足する理由を残して保留する。 |
| 適格な実観測で `p(y_observed)=0` | 採点する。log lossは `positive_infinity`、値は `null` として保存し、欠損や有限の0と区別する。 |

予測登録数、送信数、信号確定数、独立state確認数、採点可能数をそれぞれ報告する。元観測数と予測件数・モデル比較件数を混同しない。保留理由は複数あり得るため、理由別件数を合算して対象数と同じになると仮定しない。

## 6. 評価結果と訂正版を不変保存する

評価履歴には、予測IDと本体SHA、評価時点、観測ID・使用版・snapshot SHA、予測時点の定義ハッシュ、signalの元分類と採用分類、適用した訂正ID・対象別版、状態判定の根拠と判明時点、選んだstateとsignal、採点要求・結果、保留理由、DB実保存時刻を保存する。予測本体と評価結果を一つの更新可能なJSONへ上書きしない。

後日、返信signal、公開性、外部変化の影響、状態判定が訂正されたら、その事実と影響点検を新しい評価版へ記録する。**新しい分類を主たる予測評価へ自動的に差し替えない。** 旧評価はその時点で見えていた観測版・分類を保持する。公開性が取り消された場合は、現時点では採点利用を保留するviewと、過去に計算したlossを区別し、無言で削除したり過去集計を塗り替えたりしない。

特にstateが判明した後のsignal再分類は、結果を見た分類変更という漏洩候補である。現在の記述的な観測viewには適用できても、同じモデルの検証で元の点数に置き換えない。予測時の定義、元分類とその日時・実保存時刻、訂正版と根拠の利用可能時刻、state判定日時・根拠公開日時・取得日時・実保存時刻を、評価版へ固定して照合する。

訂正後の結果を別途計算する必要がある場合は、事前の評価設計がその再分類を許すか、state情報から独立した分類手順・根拠を説明できるかを点検する。不明なら主たる検証への採用を保留し、計算しても事後の感度分析として分ける。日時の順序や分類担当者の自己申告だけで、stateを見ていないことが証明されたとは扱わない。原典にない自動合格判定や、点数が改善したから訂正を採用する規則は置かない。

観測の訂正を、予測確率・カテゴリ・モデル版の訂正には使わない。予測本体の誤りが見つかっても元の確率を直して良い成績へ置き換えない。送信前に新しい予測を登録できた場合は新IDとして両方を残し、送信後なら事前予測の代替にしない。新しい定義は将来の新しい設計へ適用し、同じ質問を別IDで再登録して母数を増やさない。

モデル比較の対象モデルと評価対象は結果を見る前に固定する。複数の事前予測から事後的に一番よいものだけを採用した場合、その選択を独立した未使用データで検証済みとしない。

保存の原則は、同ID・同要求の再試行は冪等、別内容なら拒否、訂正版は連番と期待直前版によるCAS、関連書込みは原子的に成功またはrollback、callerは実保存時刻や検証結果を偽装できない、である。これらは本プロジェクトの記録契約であり、proper scoring ruleから自動的に得られる保証ではない。

## 7. 漏洩、同社依存、選択の偏りを別に点検する

- **学習漏洩：** 対象返信、後から公表されたstate判定、訂正後のラベル、評価期間の資料を、予測作成前の学習データへ戻さない。学習manifestは内容だけでなく当時の可視版と実保存時刻を示す。
- **同社依存：** 同じ会社の複数質問、同じ決算・担当部署、追伸を独立件数と仮定しない。新しい会社への一般化と、既存会社の将来予測を分け、企業groupと時間の双方を満たす分割を事前に設計する。
- **共通要因：** 企業groupの分離だけで業界・親子会社・市場共通の依存が消えたとはいえない。根拠なしに有効標本数、信頼区間、有意差を算出しない。
- **比較対象：** モデル間は同じ観測版・signal/state定義・評価時点で比較する。片方しか予測していない観測や保留案件を別に列挙し、比較可能な部分集合だけの結果を全体へ一般化しない。
- **重みと集計：** 未設定の母集団状態比率や質問型の重みを作らない。まず同じ定義のcohort・state・期間・会社ごとの件数と個別結果を保持する。単一の平均lossだけで母集団の校正や超過収益を主張しない。

予測登録と観測照合が実装されても、尤度の推定方法、未使用データでの評価設計、モデル採用の根拠は別途必要である。本契約の完成や一件の良いlossを、IR予測の校正、EVSIの正しさ、売買判断の有効性へ直結させない。

## 実装時の有限な確認項目

- 既存の観測ID・design hash・全旧snapshotを保持し、予測未登録や保留も全対象一覧に残る。
- 生成時刻の過去申告、学習manifestの未来参照、送信後の予測登録を事前予測として受理しない。
- 定義・企業・質問・モデル・snapshotの不一致、欠けた行、厳密合計の不一致を拒否する。
- 検証された実stateの一行だけを既存scorerへ渡し、未実現state・状態不明を採点しない。
- 期限内返信・無回答・遅延・同時刻衝突・公開性保留・外部変化の規則を迂回しない。
- 後日の訂正は評価の新しい版とし、as-of前の予測・観測・scoreへ混入しない。state判明後のsignal再分類は主たる予測検証へ自動採用せず、漏洩点検と事後分析を区別する。
- 再試行・版競合・途中エラーで二重計上せず、無限log lossと未観測を区別する。
